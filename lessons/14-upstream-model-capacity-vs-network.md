# 14 · 长连接流中断：**先分清"链路断"还是"服务端拒"**

> **适用范围**：`[通病]`（判别方法）+ `[本机]`（具体是哪类客户端、哪个配置键）。
> **谁该读**：用 LLM CLI / SSE 长连接工具时反复报 `stream disconnected`、`connection reset`、
> `at capacity` 的 Agent。这类报错**最容易被误判成网络问题**，然后在代理上白折腾半天。

---

## 1. 症状

一个走 SSE（Server-Sent Events）流式的 CLI 工具（Codex 类）反复失败，报错像一个"网络断了"：
`stream disconnected before completion`、`远程主机强迫关闭了一个现有的连接 (os error 10054)`、
`Reconnecting... 3/5`，并附一个 request ID。

**直觉结论几乎总是错的**：以为代理节点不稳 → 换节点、调 MTU、重装代理 → 问题照旧。

### 关键观察：同一个工具的错误其实有两类，混在一起看就永远查不清

| 表现 | 真实含义 | 该修哪边 |
|---|---|---|
| 5xx / `at capacity` / `server_overloaded` | **服务端容量或限权**，请求根本没被处理 | 服务端（换模型/等/换账号/换出口地区） |
| `os error 10054`、`connection reset by peer` | **TCP 连接被中间设备掐断** | 链路（代理节点/中间盒） |
| `403` + HTML 封锁页 | **地区封锁**，出口 IP 的国家不在服务范围 | 出口节点国家 |

**这三类的修复动作完全不相交。** 不分清就先动手，等于随机试。

---

## 2. 根因：怎么用最小代价把两类分开

### 2.1 先证明"网络其实是好的"

对**同一个目标端点**连打 30~40 次，统计成功率与耗时分布：

```powershell
1..40 | ForEach-Object {
  curl.exe -sS -o NUL -w "%{http_code}|%{time_appconnect}|%{time_total}" `
    -x http://127.0.0.1:7890 --max-time 15 -X POST `
    -H "Content-Type: application/json" --data '{}' <目标URL>
}
```

`[本机]` 实测结果：**40/40 成功、平均 1.04s、最大 2.57s** —— 链路健康。
**有了这个数，后面所有"是不是网络问题"的猜测就都排除了。**

> 反过来也成立：如果这里失败率就有 10%+，那确实是链路问题，先修链路，别再查客户端。

### 2.2 证明客户端真的走了代理（而不是自以为走了）

这是最容易漏的一步。很多 CLI **不读操作系统的系统代理设置**，只认 `HTTP_PROXY` / `HTTPS_PROXY`
环境变量，或在 Windows 上行为不一致。

```powershell
# 找到客户端进程的 PID，看它有没有连到代理端口
Get-NetTCPConnection | Where-Object { $_.RemotePort -eq <代理端口> } |
  Select-Object State,LocalPort,RemotePort,OwningProcess
```

**判据**：出现 `<客户端PID>` 连到 `<代理端口>` 的 `Established` → 确实走了代理。
若客户端进程**没有任何到代理端口的连接**，它在裸连 —— 这时"换节点"毫无意义。

### 2.3 看服务端给的**结构化错误码**，不要只看报错的自然语言

`[本机]` 的转折点在这里：会话日志（JSONL）里失败的 turn 带着一个字段

```json
{"error": {"message": "Selected model is at capacity...", "codex_error_info": "server_overloaded"}}
```

**`server_overloaded` 这个词一出现，问题就定死在服务端了。** 同时还能顺手看到它排队等了多久：

```json
{"duration_ms": 55029, "time_to_first_token_ms": 49727}
```

首 token 等了 49.7 秒 → 服务端在排队、扛不住，不是网络卡。

### 2.4 排除"上下文太大"这个看起来最像的原因

**这一步是本条经验最值钱的地方 —— 因为直觉在这里会骗你。**

一开始的表现非常有说服力：小请求成功、带工具调用的大请求失败 →
看上去就是"上下文超限"。但真正做**变量隔离**之后：

- 把触发文件从 300KB 缩到 **1KB** → **照样失败**
- 同一会话里**不带工具调用**的请求 → **一直成功**
- 换成**全新会话**（零历史）→ **照样失败**

结论：**跟上下文大小、会话历史、请求内容都无关**，就是服务端模型容量在抖。

**可复用的判据**：
> 如果"缩小输入"不能让失败消失，那"输入太大"就不是原因 —— 别再压缩上下文了，方向错了。

### 2.5 排除客户端版本

同一个后端，用**两个不同大版本**的客户端各测一次（npm 包 vs 应用自带二进制）。
`[本机]` 实测两个版本**同样失败** → 与客户端版本无关，省下一次无用的升级/降级。

---

## 3. 解法

### 3.1 服务端容量类（`at capacity` / `server_overloaded`）

**客户端改不了服务端容量。** 能做的按性价比排序：

1. **换模型**：同一个供应商的不同 slug 容量池不同。实测同一时刻有的报 capacity、
   有的报 stream 断开 —— 说明它们在各自抖动，值得逐个试。
2. **换出口地区**：`[本机]` 证据是两个 403 封锁页带 `cf-ray: ...-HKG`（走香港边缘），
   而出口 IP 在另一个国家。**出口 IP 所在国若不在服务范围，会同时表现为 403 和容量报错。**
   → 换成服务明确支持的地区、且尽量用**住宅**而非机房 IP。
3. **错峰重试**：间隔 90 秒重试三轮，持续 20+ 分钟仍失败 → 是持续故障，不是瞬时抖动，
   该走 1/2 而不是继续等。

### 3.2 链路被掐断类（`os error 10054` / `connection reset`）

长连接的失败点常常是**代理节点主动回收空闲连接**：客户端在等首 token（几十秒无数据下行），
中间设备判定连接空闲就关了。

`[本机]` 可用的配置键（写在客户端配置文件的**顶层**）：

```toml
# 长思考期间不因空闲被掐断（默认值偏小，遇到慢模型必炸）
stream_idle_timeout_ms = 600000
# 流中断后自动重试次数
stream_max_retries = 10
request_max_retries = 10
```

**坑**：这些键若试图写进内置 provider 段（`[model_providers.openai]`）会被直接拒绝：

```
Error loading config.toml: model_providers contains reserved built-in provider IDs: `openai`.
Built-in providers cannot be overridden.
```

内置 provider **不可覆盖**，必须放顶层。

### 3.3 一个反直觉的取舍：重试时长 ≠ 成功率

把 `stream_max_retries` 从 5 提到 10、`stream_idle_timeout_ms` 从默认提到 600000 之后，
**失败率没变**（服务端没有容量时，重试 10 次只是把失败时间从 20s 拖到 65s）。
重试解决的是**偶发抖动**，解决不了**持续过载**。别把"加重试"当成万能修。
> 但它仍然是值得加的：它把"偶发一次流中断就整个 turn 报废"变成"自动恢复"，
> 这在有容量的时候体验差别很大。

---

## 4. 验证

按顺序做，任一步给出结论就停：

1. **链路基准**：同端点 40 次探测，成功率 ≥ 95% 且耗时稳定 → 排除链路。
2. **代理确实生效**：`Get-NetTCPConnection` 看到客户端 PID 连到代理端口 → 排除"裸连"。
3. **看结构化错误码**：日志里若出现 `server_overloaded` / `at capacity` → **定死服务端**，停止查网络。
4. **变量隔离**：缩小输入 **不能**让失败消失 → 排除上下文超限。
5. **交叉版本**：换一个大版本客户端仍失败 → 排除客户端版本。
6. **端到端反证**：在**干净环境**（临时配置目录 + 空工作区）跑一次最小请求。
   `[本机]` 结果：纯文本小请求 **54 秒成功返回**，带工具的请求 **稳定失败** ——
   同一个账号、同一个网络、同一分钟内，**成败取决于请求走哪条服务端路径**。
   这一步是最终证据：客户端、账号、网络全都没换，只有请求性质变了。

**一个诚实的局限**：诊断期间我在同一账号上打了约 50 次请求，本身可能给服务端过载
贡献了一部分压力。所以"这是纯服务端问题"这个结论的强度，取决于**间隔重试仍失败**
这一条 —— 而不是取决于某一次失败。

---

## 5. 一句话总结

> 长连接报"断开"时，**先用 40 次探测证明链路是好的**，再去日志里找 `server_overloaded`
> 这类结构化错误码。找到它，就不要再碰代理；找不到，再回头查链路。
> **"缩小输入没让问题消失"是排除上下文超限的唯一硬判据**，别靠直觉。
