# 08 · 局域网反代：把只监听回环的 GUI 安全地开放给手机

> **适用范围**：架构 `[通病]`（"服务只绑回环 + 想在别的设备用"是极常见的需求）；
> 具体端口、包名 `[本机]`。
> **谁该读**：要把本机服务（尤其是带 Agent / 能执行命令的那种）给手机或别的电脑用的人。
> **配套代码**：`recipes/phone-gateway/`、`recipes/windows-launcher/`。

---

## 1. 为什么不能直接改 bind 地址 `[通病]`

先看清楚你要暴露的是什么：

> **这个 GUI 背后是一个能在这台机器上执行任意命令的 Agent。**

把它绑到 `0.0.0.0` 等于**把远程代码执行暴露给整个局域网**。
所以成熟的产品会**明确拒绝**这种配置（DSH 的原文理由大意是
"would expose remote code execution to the network"）——这不是"没实现"，是**故意的安全设计**。

**正确的架构：在中间加一层你自己控制的代理。**

```
手机 / 别的设备
     │  http://<LAN_IP>:<GW_PORT>/...
     ▼
┌──────────────────────────────┐
│ 你写的网关（绑 0.0.0.0）      │  ← 在这里做：认证、白名单、头重写
│  · 口令门                     │
│  · Host/Origin/Referer 重写   │
│  · HTML 注入（兼容垫片等）    │
└──────────────┬───────────────┘
               │  http://127.0.0.1:<APP_PORT>   ← 后端永远只绑回环
               ▼
        原始服务（不动它）
```

**这样做的三个好处**：

1. 后端**保持最严格的绑定**（回环），攻击面不变
2. 认证/审计/限流都集中在**你自己写的一层**上，可控
3. 后端升级换代不影响网关的职责划分

## 2. 必须重写 `Host` / `Origin` / `Referer`，否则过不了信任围栏 `[本机]`→`[通病]`

### 症状

浏览器从局域网地址打开页面，页面能加载，但**接口全部失败**，
或出现"不受信任来源"之类的拒绝。

### 根因

现代 Web 应用普遍有**来源校验**（防 DNS rebinding、防 CSRF、防跨站）：

- 它会检查请求的 `Origin` / `Referer` 是不是自己认识的那个源
- 有的还检查 `Host`（DNS rebinding 防护的常见做法）

你的请求从 `<LAN_IP>:<GW_PORT>` 来，而后端认为自己活在 `127.0.0.1:<APP_PORT>` → **不匹配 → 拒绝**。

### 解法

**转发时把这三个头改写成后端期望的值**：

```js
const upstream = 'http://127.0.0.1:3080';
const u = new URL(upstream);

headers['host']              = u.host;                 // 127.0.0.1:3080
if (headers['origin'])       headers['origin']      = u.origin;
if (headers['referer'])      headers['referer']     = headers['referer']
                                                        .replace(/^https?:\/\/[^/]+/, u.origin);
```

⚠️ **这是一把双刃剑，必须清楚代价**：
你**主动关掉了后端的一道防线**（来源校验）。所以**认证必须由你的网关来补**
（第 4 节的口令门），否则等于把门拆了。

> **[通病] 结论**：在受限服务的正前方做代理，**"让请求合法"和"补上被绕过的认证"是同一个决策的两半**。
> 只做前一半就是安全漏洞。

## 3. 流式响应与 WebSocket 也得转发 `[通病]`

现代 GUI 不只发 HTTP：

| 通道 | 你要做什么 |
|---|---|
| 普通 HTTP | 转发方法、头、体、状态码 |
| **SSE**（Server-Sent Events） | **不要缓冲**，及时 flush；长连接会挂很久 |
| **WebSocket** | 需要 **upgrade 握手转发**（`http-proxy` 类库能自动处理，手写则要处理 `upgrade` 事件与双端帧转发） |

`[本机]` 的验证证据里明确包含了 `WS /api/... -> upstream` 的长连接建立 ——
**没有这一条，"页面能打开"和"功能可用"是两回事。**

**验证时要专门断言长连接**：

- 看网关日志里有没有 upgrade 成功的记录
- 看浏览器控制台有没有 WS 报错
- 让页面产生一次**需要推送**的动作，确认实时更新真的到了

## 4. 口令门：以及一个必踩的漏网 `[本机]`→`[通病]`

### 设计

- 没通过口令的请求**一律 403**
- 口令通过后下发一个 cookie，后续请求凭 cookie 放行
- 入口 URL 带口令（`/phone?k=<口令>`），首次访问即配对

### 必踩的漏网：**浏览器拉 PWA manifest / favicon 时不带 cookie** `[通病]`

```
Failed to load manifest / 图标拿不到 / 名称是空的 / 没有全屏
```

**根因**：浏览器在**站点认证上下文建立之前**（甚至跨上下文）去取这几个资源，
**不带你刚设的 cookie** → 被你的口令门 403 → manifest 拉不到。

**解法**：**把这几个固定的、不含任何私有数据的路径加入豁免白名单**：

```
/manifest.webmanifest
/favicon.svg
（以及你的应用实际会无名拉取的其它静态资源）
```

**只豁免静态、公开、无副作用的路径** —— 不要为了省事豁免 API。

> 📌 这条的普适版本：**"认证门"要数清楚谁会不带凭据来敲门。**
> 换个场景它就是：服务健康检查探针、Webhook 回调、预检 `OPTIONS` 请求、CDN 回源、图片热链。
> 每一类都可能不带你的认证信息。

## 5. HTML 改写 vs 压缩：两个连锁细节 `[通病]`

如果你的网关要往页面里注入东西（例如兼容垫片 → [06](06-legacy-engine-compat-shim.md)）：

### ① 主动去掉 `accept-encoding`

```js
delete headers['accept-encoding'];     // 否则上游返回压缩体，你改不了
```

回环/局域网带宽不是瓶颈，**压缩在这里没有价值，而它挡住了你的改写能力**。

### ② 缓冲 + 重算 `content-length`

```js
res.setHeader('content-length', Buffer.byteLength(newBody));
```

改了 body 不改长度 → **截断或挂起**，症状非常难猜（页面加载一部分 / 浏览器一直转圈）。

**只对 `text/html` 做，其余原样流式转发。** 别把所有响应都缓冲 —— 那会毁掉 SSE。

## 6. token 轮换：让网关去追，别让客户端去追 `[本机]`→`[通病]`

后端每次重启会换入口 token。如果要求手机用户每次重新拿 token，这功能就没法用了。

**做法：网关做"token 补全"**：

```
手机访问  /phone?k=<口令>
   → 网关校验口令
   → 从固定位置读取**最新** token（由启动器维护的文件）
   → 303 重定向到  /?token=<最新>   （或直接代理时注入）
   → 200
```

**这样 token 轮换对用户完全透明。** `[本机]` 的验证专门覆盖了这一点：

> 重启后端（token 变了、PID 变了）后，**从局域网地址走带口令的入口，仍能自动补上新 token 进入 GUI**。

> 📌 **通用设计原则**：**"会变的东西"在系统里应该只有一个权威来源**（这里是那个 token 文件），
> 其它组件都从它读。谁都不许自己缓存一份。

## 7. 网络侧收尾

- **放行入站端口**（Windows 防火墙需要**管理员**创建规则）：
  ```
  规则名 DSH Phone Gateway (TCP 3081)，方向入站，动作允许
  ```
- **后端端口继续保持只绑回环**（3080）——这是架构的立足点，别为了"少一层"而动它
- **局域网 IP 会变**（换 WiFi、DHCP 续约）→ 入口地址**每次都要重新计算**，别缓存
  （`[本机]` 的做法：出二维码前**重算 LAN IP**）
- **跨公网不要直接暴露**。已有 VPN 就复用 VPN（`[本机]` 观测：用户已有 WireGuard / EasyConnect 等），
  没有的话加隧道也**远比**把端口映射到公网安全

## 8. 踩过的三个实施坑

### ① 启动脚本漏传端口环境变量 → "网关启动失败"是误报

`[本机]` 事故：启动脚本没把 `GATEWAY_PORT` 传给网关进程，网关仍绑默认端口，
而脚本去探测**新**端口 → 探不到 → 报"启动失败"。
**实际网关跑得好好的，只是跑在旧端口上。**

> 教训：**"启动失败"类断言必须核对"它到底绑在哪个端口"。**
> 传配置时要有**一处统一的传递路径**，不要让脚本和程序各有一份默认值。

### ② 二维码生成依赖 `cwd` 做模块解析

`[本机]` 事故：`Start-Process -WorkingDirectory <dir> ... -Wait` 形式实测 `ExitCode=1` 且不产出文件；
改成"直接调用 + `Push-Location`"就正常。

> 教训：**依赖 `cwd` 解析模块的脚本，不要用"另起进程 + 指定工作目录"的方式调用。**
> 要么在脚本里显式 `chdir`，要么直接用当前进程调用。

### ③ **绝不要批量 kill node 进程**

`[本机]` 事故：为了"重启"，按名字批量杀 node → 把宿主自己的后台任务运行器一起杀了，
**该会话永久失去后台任务能力**。

→ 完整复盘见 [03](03-sandbox-stdio-limits.md) 第 3 节。这是本库**最贵的教训**。
