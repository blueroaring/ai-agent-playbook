# 12 · 学术数据源 API 的真实行为（Scholar / arXiv / dblp / OpenAlex / Crossref + Zotero 写入）

**适用场景**：你要做一个"自动检索论文 / 文献雷达 / 综述助手"之类的系统，需要把多个学术数据源
聚合起来，并且要写回 Zotero 之类的外部文献库。
**一句话价值**：这五个源里有 **四个** 的行为和官方文档给人的印象不一样；照文档写会在真实网络下大面积失败。

结论基于 2026-09-15 的一次完整实现（自建 `paper-radar` 项目）与当时的实测记录。
**每条都请先跑「验证」再套用** —— 数据源的限流策略和反爬策略会随时间变化。

## 1. 先看这张可用性表（这是全篇最重要的部分）`[本机]`

| 源 | 官方 API | 需要 key | 实测结果 | 提供的关键字段 |
|---|---|---|---|---|
| OpenAlex | ✅ | 否 | **始终可用**，无 key 也稳 | venue、年份、引用数、作者、摘要（倒排索引） |
| Crossref | ✅ | 否 | 可用；**连续快速请求会 429** | venue、DOI、作者、引用数（多数无摘要） |
| Google Scholar | ❌ 无官方 API | 否 | 页面解析可用，**必须低频 + 真浏览器 UA** | 全量程覆盖、引用数（无 DOI） |
| arXiv | ✅ 有官方 API | 否 | **官方 API 429 / 超时**；`rss.arxiv.org` 可用 | 预印本、完整摘要 |
| dblp | ✅ | 否 | **返回反爬挑战页，纯 HTTP 客户端不可用** | 计算机专用、规范会议名 |
| Semantic Scholar | ✅ | 可选 | 无 key 时 **几乎必然 429** | 引用数、领域 |

**由此得出的架构结论**（比具体某源更值得记）：

> **数据源必须能"单独失败"**。不要写"全部成功才算成功"的聚合逻辑，
> 而是每个源在自己的线程/协程里跑，异常收敛成 `errors = {源: 原因}` 返回给上层。
> 上表里任意一行明天变成"不可用"都不该让你整个系统瘫掉。

**验证**：对每个源发一个真实查询，打印 `{源: 条数或异常}`。
如果某个源在你的网络下失败，先别改代码 —— 换网络/挂代理再试一次，区分"源挂了"和"我的链路挂了"。

## 2. Google Scholar 只能页面解析，且必须按域名限速 `[通病]`

**症状**：请求返回 200 但内容是人机校验页；或连续几次后全部失败。

**根因**：没有官方 API；UA、频率、Referer 任一不达标就触发拦截。

**解法**（四条一起做才有用）：

1. **带真实浏览器 UA**，别用 `python-requests/2.x` 这类默认 UA；
2. **按域名限速**：同一 host 的两次请求间隔 ≥5 秒，且**串行化**（加锁），
   否则多线程并发会在你限速生效前就已经打出十几发；
3. **识别校验页**：正文里出现 `not a robot` / `unusual traffic` 就**立即放弃本数据源**，
   别重试（越重试越糟），把它当成"本次跳过"；
4. **解析逻辑写成纯函数**（`parse_scholar_html(html) -> list[Paper]`），网络调用与解析分开 ——
   这样可以用固定 HTML 做离线单测，对方改版时你能立刻定位是解析挂了还是网络挂了。

结果块的结构（2026-09 实测，可直接照抄选择器思路）：
每条结果是 `<div class="gs_r ...">`，标题在 `h3.gs_rt` 的 `<a>` 里，
作者/会议/年份挤在 `div.gs_a` 里用 ` - ` 分隔，摘要在 `div.gs_rs`，
引用数在 `div.gs_fl` 里匹配 `Cited by (\d+)`。
**按 `<div class="gs_r` 的出现位置切片**比嵌套 div 匹配稳得多（不需要 HTML 解析库）。

**验证**：连续请求 6 次，观察是否出现校验页；用离线 fixture 断言字段解析正确。

## 3. arXiv：官方 API 被限流时，用分类 RSS 兜底 `[通病]`

**症状**：`export.arxiv.org/api/query` 返回 **429 Too Many Requests**，或直接读超时；
换成 `http://` 也 429，挂代理也一样（说明是按出口 IP 限的）。

**关键发现**：
- `https://rss.arxiv.org/rss/cs.NI`（按分类）**可用**，返回最近一次公告的全部论文；
- 它**不支持检索式**，只能本地按关键词过滤；
- 但字段够用：`title` / `link` / `description`（含完整摘要）/ `dc:creator`（逗号分隔作者）/
  `pubDate` / `arxiv:DOI` / `arxiv:announce_type`；
- `description` 的格式是 `arXiv:<id>v1 Announce Type: new \nAbstract: <正文>`，
  需要切掉前缀才能当摘要用。

**解法**：给 arXiv 插件做**双通道**：先试官方 API，失败再走 RSS，并在日志里说清走了哪条路。
对"每日最新论文"这个场景，RSS 其实比 API 更合适（它本来就是"最新公告"）。
RSS 只覆盖最近公告，所以要明确告诉用户"这是降级路径，历史检索不全"。

**验证**：先 `curl` 官方 API 确认确实 429，再确认 RSS 能返回 item；
然后用一个与 RSS 内容无关的检索词，确认本地过滤**不会**把整批公告塞进结果。

## 4. dblp 对纯 HTTP 客户端返回反爬挑战页 `[本机]`

**症状**：请求 dblp 搜索 API，`json.loads` 报 `Expecting value: line 1 column 1`；
换成 XML 格式也一样；`Invoke-WebRequest` 报"连接被意外关闭"。

**根因**：响应体其实是 HTML，标题类似 `Making sure you're not a robot`
（Anubis / Cloudflare 一类的 JS 挑战），需要执行 JS 才能拿到真数据。

**解法**：
- 纯 HTTP 客户端**没有干净的绕过办法**，不要在这上面耗时间；
- 用 **Crossref 替代它**拿到"发表在哪里"（IEEE/ACM/Elsevier/Springer 都注册了 DOI，venue 质量够用）；
- 把 dblp 插件**保留但默认关闭**，并在 README 写明"需要你的网络能直连"。

**验证**：请求一次，看响应体是不是 `<!doctype html>` + `not a robot` 字样。
是 → 直接放弃该源，不要加大重试次数。

## 5. 用标题去学术库"认领"论文，必须加相似度闸门 `[通病]`

**症状**：用户粘贴一篇论文的**完整标题**当种子，系统却认领成了另一篇毫不相关的论文。

**根因**：OpenAlex / Semantic Scholar 的 `search` 是**模糊检索**，不是精确匹配。
把一篇库里没有的论文标题丢进去，它会**热情地返回最接近的一篇**，而不是返回空。
实测：`Themis: Scheduling-Aware Buffer Management for HBM-Based Hybrid Buffers`
被匹配成了标题只有 3 个字母的 `HSM`。

**解法**：拿到候选后**自己校验相似度**，不达标就当"没找到"：

```python
import difflib, re

def title_similarity(left, right):
    a = re.sub(r"[^a-z0-9]+", " ", (left or "").lower()).strip()
    b = re.sub(r"[^a-z0-9]+", " ", (right or "").lower()).strip()
    if not a or not b:
        return 0.0
    if a == b:
        return 1.0
    ratio = difflib.SequenceMatcher(None, a, b).ratio()
    ta, tb = set(a.split()), set(b.split())
    coverage = len(ta & tb) / max(1, min(len(ta), len(tb)))   # 只看覆盖率会漏词序差异
    if a in b or b in a:
        ratio = max(ratio, 0.95)
    return max(ratio, coverage)
```

阈值取 **0.8**：实测"完整标题 vs 同一个完整标题"=1.0，"
无关短标题"≈0.05，而**碰巧共享几个词的短标题能到 0.75** ——
所以 0.72 太松，0.8 才安全。**宁可解析不出来**（把原文本喂给关键词抽取），
**也不要塞一篇错的论文进去** —— 后者会污染整个推荐方向，且用户很难发现。

**验证**：构造三组用例：完全相同标题（≈1.0）、无关短标题（<0.5）、
共享少量词的短标题（应低于阈值）。这是纯函数，放进单测。

## 6. Crossref：加 `mailto` 进 polite pool，否则必然 429 `[通病]`

**症状**：Crossref 前几次请求成功，连续 6 条检索式后开始 429。

**解法**：
- 请求里带 `mailto=you@example.com`（Crossref 的 polite pool，**不是 key，只是联系方式**）；
- 同时把该域名的请求间隔调到 ≥1.5 秒；
- OpenAlex 也支持 `mailto`，同理。

**注意**：`mailto` 在源码里要留成配置项，别硬编码成作者邮箱 —— 你写的是要给别人复用的代码。

**验证**：完整跑一次"N 条检索式"的批量请求，确认 0 个 429。

## 7. 跨源去重：单靠 DOI 或单靠标题都不行 `[通病]`

**症状**：推荐表里同一篇论文出现两次（一次来自 OpenAlex，一次来自 Google Scholar）。

**根因**：
- **只用 DOI**：Google Scholar 的条目**没有 DOI**，永远合并不上；
- **只用标题**：会把同名不同文的文章（综述、Editorial）错误合并。

**解法**：两级判定 ——
① 按 `DOI → arXiv ID → 归一化标题哈希` 生成指纹分组；
② 再做一轮**归一化标题完全相同**的合并（把有 DOI 的组和无 DOI 的组并起来）。
实现时注意：合并后多个指纹会指向同一个对象，**输出前必须按对象身份去重**，否则会重复。

**验证**：构造"同标题 + 一方有 DOI"和"同 DOI + 标题格式不同"两组用例，断言结果长度都是 1。

### 7.1 只做"单次检索内去重"是不够的 —— 跨运行会重新裂开 `[通病]`

**症状**：单次检索结果里没有重复，但用了一段时间后**清单里出现成对的重复条目**，
而且两条元数据不一样（一条有 DOI、一条没有；一条 venue 是 arXiv、一条是会议名）。

**根因**：上一节的去重只作用于**本次抓回来的那批结果**。若
第 1 天只有无 DOI 的源命中这篇论文，它以 `title:<hash>` 落库；
第 2 天带 DOI 的源命中同一篇，它以 `doi:<hash>` 落库。
两次运行各自的批次内部都没有重复，于是库里出现**两行同一篇论文**。

**隐蔽性**：它随使用时间逐渐浮现，**在单次运行的测试里完全看不出来**。
凡是"以内容指纹做主键"的聚合系统都会踩，不只是文献库。

**解法**：把身份判定从"批次内"提升到"库级"，并允许显式指定**规范键**：

```python
# 1) 落库时记录归一化标题并建索引
CREATE INDEX idx_papers_title_norm ON papers(title_norm)

# 2) 写库之前，把本轮结果的 key 对齐到库里已存在的记录
index = store.title_key_index()          # {归一化标题: 已存在的 key}
for paper in results:
    existing = index.get(normalize_title(paper.title))
    if existing and existing != paper.key:
        paper.canonical_key = existing    # 强制复用旧键
    else:
        index.setdefault(normalize_title(paper.title), paper.key)
```

关键点：**模型必须支持覆盖主键**（`key` 属性返回 `canonical_key or 指纹`）。
只靠计算属性的话，key 永远由字段决定，"对齐到旧键"这件事根本没地方表达。

配套还要一个**修历史数据的一次性作业**（合并重复行 + 把引用它们的子表记录一起搬迁）：
按归一化标题分组 → 保留"最正式"的键（DOI > arXiv > 标题哈希）→
子表记录搬到保留键 → 删掉被合并的行 → **最后断言子表里没有孤儿**。

⚠️ 搬迁子表要分清主键形态：
- 单列主键（如 `remembered(paper_key)`、`zotero_links(paper_key)`）用
  `INSERT OR IGNORE` + `DELETE`，不能直接 `UPDATE`（保留键下可能已有一条，会冲突）；
- 复合主键（如 `recommendations(topic_id, paper_key)`）必须 `INSERT OR IGNORE ... SELECT`，
  冲突就丢新记录、保留原有那条。

**字段合并要按"质量"取优，不能先到先得** —— 这一步最容易漏。真实案例：
两行合并后留下了 arXiv 那条，于是「发表在哪里」长期显示 `arXiv (Cornell University)`，
而这篇文章其实发表在 EuroSys。解法是给字段定义质量函数
（正式会议/期刊 > 预印本仓库 > 空），合并时取更优者，并且
**在 upsert 时同样只升不降**（否则后续某次只有 arXiv 结果时又会降级回去）。

**验证**（三条都要）：
1. 构造"第一轮无 DOI、第二轮有 DOI"的顺序，断言库里只有 1 行；
2. 对人为造出的重复行跑修复作业，断言子表**零孤儿**且幂等（再跑一次改动为 0）；
3. 构造"正式 venue 先存、预印本 venue 后到"的顺序，断言 venue 没被降级。

### 7.2 身份保证要放在**存储层**，不要只放在某一个调用方里 `[通病]`

**症状**：在同一处加了身份对齐后，换一条写入路径（CLI 命令、回填作业、定时任务）
又冒出了重复行。测试里也复现了：直接调 `upsert()` 就会分裂。

**根因**：只在**采集/编排层**（"检索一次"这个函数）做对齐，等于把不变量押在
"所有调用方都记得先对齐"上。写入路径越多，漏掉一条只是时间问题。

**解法**：把不变量放进**拥有数据的那个方法**里 —— 谁写主表，谁保证身份：

```python
def upsert_papers(self, papers):
    for paper in papers:
        norm = normalize_title(paper.title)
        existing = self.conn.execute(
            "SELECT key FROM papers WHERE title_norm = ? LIMIT 1", (norm,)
        ).fetchone()
        key = existing["key"] if existing else paper.key
        if existing and existing["key"] != paper.key:
            paper.canonical_key = existing["key"]   # 让内存对象与落库身份一致
        ...  # 用 key 写入
```

编排层那次对齐可以保留（省一次查询、且让同一批结果内部一致），但**它不再是唯一防线**。

⚠️ **副作用要预期到**：兜底加上后，"造重复行"这件事本身变难了 ——
原来用来测"修复作业"的测试会因为造不出脏数据而失败。
这不是测试坏了，而是**修复生效的证据**；正确做法是改用**原始 SQL 直接写入**来伪造历史脏数据，
继续覆盖修复作业本身。

**同类推论**：另两个字段（发表处、DOI）也适用"只升不降"——
出版社 DOI 优先于仓储 DOI（arXiv 的 DataCite DOI `10.48550/arxiv.*` 应让位于 `10.1145/...`）；
正式会议名优先于预印本占位名。**每条都要在"合并"与"落库"两处同时实现**，
只在合并处做的话，后续某次只有预印本源命中时又会把它降级回去。

**验证**：写一个测试直接调 `upsert()`（不经过编排层）造"两轮不同标识的同一篇论文"，
断言库里只有 1 行。

## 8. Zotero Web API：写入后立刻查重查不到 `[通病]`

**症状**：调用 Zotero Web API 成功创建条目，**紧接着**用 `GET /items?q=<DOI>` 查重却返回空。
后果：用户连点两次"加入文献库"，就产生两条重复条目。

**根因**：Zotero 的**搜索索引是异步的**，新建条目不会立刻出现在 `q=` 搜索结果里。

**解法**（两层防护，都要）：
1. **本地幂等表**：写入成功后在本地库记 `paper_key → zotero_key`，
   下次入库前先查本地表；这一层立刻生效，不受索引延迟影响；
2. **远端查重保留**：用来兜住"用户在别处手动加过"的情况（延迟几秒到几分钟后就能查到）。

配套的两个小坑：
- 批量创建走 `POST /users/<id>/items`（数组，**单次最多 50 条**），
  响应是 `{successful: {"0": {key, version}}, failed: {...}}`，**按下标对应输入数组**；
- **删除**条目要带 `If-Unmodified-Since-Version: <version>` 头（version 来自创建响应），
  所以创建时就要把 version 存下来，别只存 key。
- **不填 userID 也行**：`GET /keys/<api_key>` 会返回 `userID`，比让用户去设置页抄数字友好得多。

**验证**：写入 → 立刻再写入一次 → 断言第二次是 `duplicate`；
然后删除验证条目（用 version 头），确认 `deleted: 1`。**测试要能自己回滚**，别在别人库里留垃圾。

## 9. 顺手记下的几个跨领域小坑 `[通病]`

| 坑 | 现象 | 解法 |
|---|---|---|
| Windows 文件名不能含 `:` | 用 `formatdate()` 生成的文件名写盘报 `OSError: [Errno 22] Invalid argument` | 时间戳整段做白名单过滤（只留字母数字和 `-_`） |
| 单一全局超时不够用 | 一个慢源（arXiv）拖慢整批请求 | HTTP 客户端支持**按域名**覆盖 `timeout` / `retries` / `min_interval` |
| "定时任务"补跑会吓人一跳 | 晚上启动服务，立刻收到一封早报 | 补跑要加**时间窗口**（如只在目标时间后 180 分钟内补跑），窗口外标记"今日已处理" |
| 定时判断用"当天是否跑过" | 改了时间后当天不再触发 | 用 `日期+时间` 作为账目 key，而不是日期 |
| LLM 最贵，别给垃圾候选花钱 | 一次检索几十篇都去调用大模型 | 把"检索"与"生成卡片"拆成两个方法：先按规则筛到 Top-N，再为 Top-N 调 LLM |
| **"只读"的采集函数 + 另一个调用方** | 某条链路写了子表却从没写主表，留下指向不存在记录的孤儿行（界面用 INNER JOIN 还看不出来） | 约定"谁写子表谁负责主表"，或在写子表前统一 upsert 一次；定期跑孤儿检查 |
| 阈值/开关类配置只存在代码默认值里 | 用户想调却要改代码 | 阈值全部走配置 + 界面可改；并且**调高阈值不要删除已有数据**（只影响高亮/过滤），删除必须是显式动作 |
| **把自己给过的东西又推回给用户** | 用户提供的种子/收藏被数据源反复抓到，一路当成"新结果" | 见第 10 节：**用户已知的输入必须从推荐结果里排除** |
| **服务端 404，但文件明明在磁盘上** | 文件名含中文/空格，浏览器发的是**百分号编码**路径，服务端没解码 | 解析路径前先 `urllib.parse.unquote()`；取 basename 顺带挡路径穿越 |

## 10. 推荐系统必做：**把用户已经知道的东西排除掉** `[通病]`

**症状**：用户明确给了几篇"种子论文"作为研究方向的起点，几天后系统把这些种子
**当成新论文推荐回来**，甚至发进了每日邮件。用户的观感是"你把我已经给过你的东西又发给我"。

**根因**：种子只被用来**推导检索方向**（生成关键词与检索式），却**从来没被用来过滤结果**。
而这些论文恰恰是检索式最可能命中的 —— 它们就在这个方向的正中央。
所以"最相关的论文"里必然包含用户自己的种子。

**这个坑的普遍性**：任何"用户给几个样例 → 系统找相似的"功能都有同一个洞 ——
你让系统往用户已经指过的方向找，找到的第一批就是用户指过的东西。

**解法**：

```python
# 1) 把"已知集合"归一化成多种标识（一种不够：不同来源给的字段不一样）
def known_index(items) -> dict[str, set[str]]:
    index = {"doi": set(), "arxiv": set(), "title": set()}
    for item in items:
        blob = " ".join(filter(None, [item.doi, item.arxiv_id, item.title, item.raw]))
        index["doi"].update(x.rstrip(".").lower() for x in DOI_RE.findall(blob))
        index["arxiv"].update(ARXIV_RE.findall(blob))
        norm = normalize_title(item.title)
        if len(norm.split()) >= 3:          # 太短的多半是 ID，不是标题
            index["title"].add(norm)
    return index

# 2) 在**唯一的候选出口**上过滤（不要在每个调用方各写一遍）
def collect(self, topic, ...):
    ranked = rank(...)
    ranked, excluded = self.exclude_known(topic, ranked)   # 手动检索与定时任务共用
    return {"papers": ranked, ...}
```

**三个必须注意的细节**：

1. **只用一种标识不够**。同一篇论文在库里可能只存了标题（那轮没拿到 DOI），
   而这一轮带上了 DOI —— 三种都要建集合，且**标题必须归一化**。
   实测：`Themis:{Scheduling-Aware} Buffer Management for {HBM-Based} Hybrid Buffers`
   与 `Themis: Scheduling-Aware Buffer Management for HBM-Based Hybrid Buffers`
   归一化后相等（`{}` `:` 都被压成空格）。
2. **正则别把 DOI 里的数字读成 ID**。`10.1145/3689031.3717495` 能匹配出 `9031.37174`，
   被当成 arXiv ID 混进已知集合，进而**误排除无关论文**。
   加两道约束即可：**年月必须合法**（`\d{2}(0[1-9]|1[0-2])`）+ 前后加边界。
3. **顺带排除"用户已在别处收藏过的"**：本地只要有一张"已同步到外部工具"的映射表就能
   零成本过滤；远端查重留给真正要写入的那一刻。

**验证**：构造"种子出现在结果里"的场景，断言过滤后**不含**种子
（按标题、按 DOI、按 arXiv 三种各断言一次），并断言关掉开关后原样返回。

**真实的连带损失**：这次故障还有副作用 —— 被推回来的种子会**挤占当天的推荐名额**
（每天只有 top_n 条），用户因此少收到一篇真正的新论文。
排除已知项不只是体验问题，它直接浪费了推荐额度。

## 11. 让模型指认"领域源头"，必须过**两道闸门** `[通病]`

**场景**：要做一个"从该领域的奠基工作出发、按年份往下"的脉络视图（例如用户说
"交换机缓冲管理的始祖是 DT"）。起点由谁定？让 LLM 回答"这个方向最早的奠基性工作是什么"。

**好消息**：模型在这件事上表现很好。实测一次就给出了该子方向的经典论文
（`Dynamic Queue Length Thresholds for Shared-Memory Packet Switches`, Choudhury & Hahne, 1998），
并准确说明"首次提出按队列占用动态调整共享缓存阈值"。

**坏消息**：**它给的东西不能直接用**。同一个问题问两次，第二次给的是完全不同的四篇，
其中第一篇是 `Dynamics of TCP traffic over ATM networks` —— 真实存在（被引 400+），
但研究的是 TCP/ATM 拥塞控制，**属于别的子方向**。还有一篇的作者串直接是编的
（`R. R. C. B. S. et al.`）。

### 两道闸门

```python
def resolve_origin(candidate_title: str, topic) -> Paper | None:
    # 闸门一：存在性 —— 回学术库按标题检索，必须过相似度阈值
    paper = search_library_by_title(candidate_title, threshold=0.8)
    if paper is None:
        return None                       # 模型记错了 / 编的 → 丢掉

    # 闸门二：切题 —— 必须命中这个方向的关键词
    hits, _ = match_keywords(paper, topic.keywords)
    if len(hits) < MIN_KEYWORD_HITS:       # 例如 2
        return None                       # 真实存在，但属于别的子方向 → 丢掉

    return paper
```

**为什么两道都要**：
- 只做存在性 → 放过"真实但跑题"的早期工作，脉络从**错误的源头**开始，
  后面整条时间线都会被带偏（这是最难发现的错，因为每一篇都是真论文）；
- 只做切题 → 编造的标题可能因为关键词碰巧命中而蒙混过关。

**手填输入也不能松**：允许用户直接指定起点（他们比模型更清楚），
但**手填标题同样要过相似度闸门，而且阈值不能比自动提名松**。
实测阈值 0.6 时，`Buffer Management in a Packet Switch with Shared Memory`
被匹到了另一篇 2000 年的论文；收到 0.8 才正确。

### 两条配套的设计结论

1. **同类实体的过滤要放在唯一出口上**。种子、已收藏、已判定过的……这类"已知集合"
   的排除逻辑，写在采集函数的出口（检索与定时任务共用的那一处）就不会漏；
   写在每个调用方里，迟早漏一个（见第 10 节）。
2. **部分构造的对象在序列化时会覆盖已算好的值**。同一次开发里的真实 bug：
   不走模型摘要的路径只构造 `Recommendation(paper=p)`，而它的 `to_dict()` 把
   `score` 写成自身默认值 **0**，覆盖了论文上已经算好的分数 —— 界面整列相关度全是 0。
   **凡是"从 A 构造 B 再序列化 B"的地方，都要检查 B 的默认值会不会盖掉 A 的实值。**

**验证**：
- 断言"真实但跑题"的候选被挡掉（用一篇和方向无关的经典论文做反例）；
- 断言手填起点时不调用模型（少一次付费调用，也少一次被带偏的机会）；
- 断言脉络输出的年份序列**单调不减**，且起点永远排第一。

## 一句话总结

**学术数据源是"尽力而为"的异构拼盘**：官方文档描述的是理想情况，真实世界里
四个源里有四个会以不同方式失败。正确的架构不是"找到能全都能用的源"，
而是**让每个源独立失败、让每个站点的解析逻辑可离线测试、让最贵的那一步（LLM）只处理筛完的候选**。

再补一句这一节学到的：**模型擅长"给候选"，不擅长"保证正确"**。
凡是模型给出的**标识性内容**（标题、ID、链接、人名），都必须回到确定性数据源校验；
只有**判断性内容**（为什么算奠基、属于哪一类）才可以直接采信。
