# 01 · 验证纪律 —— 为什么你的"测试通过"有一半是假的

> **适用范围**：`[通病]` 元经验，与语言和平台无关。
> **谁该读**：所有 Agent。这是本库最该先读的一篇——它决定了你能否信任自己后面的所有结论。

Agent 最容易犯的不是"不会做"，而是**做完了以为做成了**。
下面五个事故都是真实发生过的，每一个都通过了当时的"验证"。

---

## 事故 1：`delete eval('globalThis.X')` —— 假通过之王 `[通病]`

**场景**：要验证一个"旧浏览器内核兼容垫片"是否真的生效，思路是**主动删掉现代 API 来模拟旧内核**，然后看页面是否还正常。

**当时的代码**：

```js
await page.addInitScript(() => {
  delete eval('globalThis.Iterator');
  delete eval('AbortSignal.any');
});
```

**结果**：页面正常，零错误 —— 判定"垫片没被触发，所以现代浏览器上无副作用"。

**真相**：`delete` **不能作用于表达式的结果**，只能作用于引用。`eval('globalThis.Iterator')` 是一个表达式，
求值得到 `Iterator` 的值（一个函数对象），`delete <值>` 在非严格模式下**静默返回 `true` 但什么都没删**。
所以那一步**一个 API 都没删掉**，模拟旧内核从头到尾没有发生。测试通过，是因为被测对象压根没被施加压力。

暴露它的证据是什么？垫片自己会报告"我补了哪些 API"：

```js
globalThis.__phoneGatewayShimmed   // []
```

**空数组**。当时差点把这行读成"垫片正确地跳过了"。

**正解**：

```js
await page.addInitScript(() => {
  delete globalThis.Iterator;      // 直接引用，合法删除
  delete AbortSignal.any;
});
// 断言必须是非空的：
// __phoneGatewayShimmed === ['Iterator','AbortSignal.any', ...]
```

> ### 📌 可迁移的规则
> **断言要能区分"发生了"和"没发生"。**
> 一个"没有报错"的验证，必须配一个"如果我做错了就会报错"的**阳性对照**。
> 具体到本事故：不要断言"页面正常"，要断言"垫片报告它补了 N 个 API，且 N > 0"。
>
> **更通用的形式**：任何"模拟条件"的代码，都要问一句 —— **我给系统施加压力了吗？怎么证明？**
> 删 API、断网、塞脏数据、注入延迟，都要有一个可观测的"确实做了"的信号。

## 事故 2：把 `[本机]` 观测当成 `[通病]` 结论 `[通病]`

**场景**：在某台机器上确认"端口 9080 空闲"，于是把服务默认端口写死为 9080。

**真相**：9080 被一个**毫不相关的系统服务**占用着。所谓"确认空闲"是探测逻辑被骗了
（详见 [09](09-godot-automation.md) 第 3 节）。换台机器可能换一个服务占用它，也可能真的空闲。

**教训**：**"我这台机器上成立"和"成立"是两件事。**
本库用 `[通病]` / `[本机]` 两种标记强制区分它们。你在自己的笔记里也请这么做。

---

## 事故 3：修好了，但你看的是旧状态 `[通病]`

**场景**：改了宿主配置，浏览器里立刻复现一个报错："`directoryPicker.pick` needs the native capability;
the composed picker serves "browse""。看起来是改错了。

**真相**：那个页面是**热重载之前**加载的旧前端 bundle（旧 surface）与**新的**宿主后端不匹配。
**刷新一次就好了**，配置本身是对的。

**教训**：报告错误之前，先确认**你观测的东西是不是当前状态**：

- 页面 → 是否在新 context / 刷新后？
- 进程 → PID 是不是新的？（重启后 PID 会变）
- 缓存 → 是读缓存还是读源？
- 配置文件 → 改了文件，宿主**重载了吗**？

---

## 事故 4：改了代码，但没有触发重新组合 `[通病]`

**场景**：安装/升级一个插件后，行为毫无变化。反复检查配置，配置是对的。

**真相**：这类体系（bundle、插件树、路由表）**只在宿主进程启动时组合一次**，
文件系统上的变更不会自动生效。必须**重启宿主进程**。
（DSH 的例子见 [07](07-dsh-harness-internals.md) 第 2 节。）

**教训**：改完任何配置，先分类回答一个问题：

| 变更类型 | 生效方式 |
|---|---|
| 数据、内容文件 | 立即（下次读取） |
| 有明确热重载声明的配置 | 立即（或需手动 reload） |
| 插件 / bundle / 依赖 / 路由表 / 启动图 | **必然需要重启进程** |

**不确定的时候，去实测一次"改一个无害的值，看是否生效"**，比读文档快。

## 事故 5：把中间产物当成了最终证据 `[通病]`

**场景**：给启动器加 `-NoQr` 开关，要求"双击快捷方式不出二维码"。验证方式是"运行一次，看看输出里有没有 QR 字样"。

**真相**：输出干净，但**二维码文件可能被别的东西重新生成**。更可靠的证据是**比较产物本身的修改时间**：

```powershell
$before = (Get-Item .\phone-qr.png).LastWriteTime
& .\start.ps1 -NoQr -NoBrowser
$after  = (Get-Item .\phone-qr.png).LastWriteTime
$before -eq $after      # True → 确实没重新生成
```

**教训**：**用最终产物做断言，不要用过程日志做断言。**
日志可以被跳过，产物不会撒谎。

---

## 事故 6：验证"打开了网页/窗口"时，四种假证据 `[通病]`

**场景**：要验证"双击桌面快捷方式能直接打开网页"。我先后拿到四类"看起来通过了"的证据，
**其中三类全是假的**：

| 我当时的观测 | 为什么它是假证据 |
|---|---|
| `cmd /c start "" "X.lnk"` 退出码 0 | **`start` 对带空格的 `.lnk` 路径常常什么都不启动**，退出码照样是 0。测试手法本身是错的 |
| 浏览器进程数 21 → 21，没变化 | **已有浏览器实例时，打开新标签不会新建进程**。数量不变什么也不能证明 |
| 扫所有浏览器进程的命令行，没有 URL | 新标签是**由已有进程通过 IPC 打开的**，URL 永远不会出现在任何命令行里 |
| 启动器打印了 "Opened ... in the default browser" | 那是**过程日志**，正是事故 5 说的假证据 |

**真正的解法：把"外部世界是否真的访问了我"变成服务端的可观测事实。**

给被测服务加一个**访问日志**开关，然后清空日志 → 触发动作 → 看日志里有没有那条请求：

```powershell
# 用运行时推导的路径，别把绝对家目录路径写进文档
$lnk = Join-Path ([Environment]::GetFolderPath("Desktop")) "My App.lnk"

Remove-Item .\data\access.log -ErrorAction SilentlyContinue
Start-Process $lnk                                   # 等价于双击
Start-Sleep -Seconds 10
Get-Content .\data\access.log                        # 期望看到 GET / 200
```

实测输出（这才是证据）：

```
15/Sep/2026 18:24:29 127.0.0.1 "GET / HTTP/1.1" 200 -
15/Sep/2026 18:24:29 127.0.0.1 "GET /style.css HTTP/1.1" 200 -
15/Sep/2026 18:24:29 127.0.0.1 "GET /app.js HTTP/1.1" 200 -
```

**顺带两条可复用的结论**：

1. **模拟"双击快捷方式"要用 ShellExecute，不要用 `cmd start`**：

   ```powershell
   Start-Process $lnk                        # 走 ShellExecute，与资源管理器双击同一条路
   # 或 COM： (New-Object -ComObject Shell.Application).ShellExecute($lnk, "", $wd, "open", 0)
   ```
   我一开始用 `cmd /c start` 得到"日志为空"，差点去改本来正确的启动器 ——
   **先怀疑测试手法，再怀疑被测对象**。

2. **给自己的本地服务留一个访问日志开关，比什么都好用。**
   "浏览器到底请求到没有""是不是打到了我这个服务"这类问题，
   只有服务端记录能回答。默认静音 + 一个 `access_log: false` 开关是最佳平衡
   （记得给日志文件加体积上限，否则会长到失控）。

**教训**：**当被测对象在"另一个进程/另一个窗口"里时，不要从外面猜它做了什么 ——
让被访问的一方留下记录。** 观测点要放在**因果链的末端**（请求真的到达了），
而不是**前端**（我发起了请求）。

## 事故 7：**空结果**和**探测失败**长得一模一样 `[通病]`

**场景**：排查"为什么定时任务没跑"。我用了这一句来列任务：

```powershell
Get-ScheduledTask -ErrorAction SilentlyContinue | Where-Object { $_.TaskName -match "Paper|Radar" }
```

输出为空。我据此写下结论："**任务不存在了**" —— 然后准备重新注册。

**真相**：那一刻沙箱限制了任务计划程序接口，`Get-ScheduledTask` 本身失败了。
`-ErrorAction SilentlyContinue` 把那个错误**吃掉**了，于是"报错"变成了"空列表"。
（同一次排查里，`schtasks.exe` 和 COM 接口都失败了，说明是环境限制，不是任务没了。）

**救回来的一步：对照实验。** 我对一个**确定存在**的样本（前一天刚跑过的另一个任务）
跑**同一个探测**：

```powershell
schtasks /Query /TN "AI-Agent-Playbook-Publish"   # 确定存在
schtasks /Query /TN "MyTask"
schtasks /Query /TN "Definitely-Not-Exist-12345" # 确定不存在
```

**三个都报同一个错** → 探测手段本身坏了，结论作废。
（另一次用磁盘取证确认任务确实存在：任务计划程序把每个任务存成 XML，
`C:\Windows\System32\Tasks\<任务名>` —— 绕开接口直接看文件。）

**教训**：

1. **在"探测手段可能失效"的环境里，任何空结果都必须先做对照实验** ——
   对一个已知为**正**的样本和一个已知为**负**的样本各跑一次。
   三者表现一致（都空/都报错）就说明是工具问题，不是事实。
2. **`-ErrorAction SilentlyContinue` 是危险默认值**，用在排查阶段等于自断线索。
   排查时先用 `-ErrorAction Stop` 或显式捕获，看清到底是"没有"还是"查不到"。
3. **多准备一条独立取证路径**（这里：磁盘上的任务定义 XML vs 接口查询）。
   当接口不可用时，文件系统通常仍然可读 —— 两条路径结论一致才算事实。

**顺带**：这个事故和事故 3（"看的是旧状态"）、事故 5（"把过程当证据"）是同一族 ——
**你的观测工具本身也是需要被怀疑的对象。**

## 一套可复用的验证清单

每次声称"完成"之前，过一遍这四问：

### ① 我的断言能否被证伪？

如果"做错了"和"做对了"会产生**同一个观测结果**，那这个断言一文不值。

- ❌ "命令没有报错" → 做错了也可能不报错
- ✅ "文件大小从 0 变成 3840 字节" → 做错了就是 0

### ② 我验证的是路径还是结果？

- ❌ 验证"我调用了保存接口"
- ✅ 验证"**磁盘上的文件里真的出现了那个节点**"（→ 参见 [09](09-godot-automation.md) 的视觉闭环）

**端到端副作用的强度排序**（越靠后越可信）：

```
返回值 < 日志 < 内存状态 < 进程状态 < 磁盘文件 < 另一个进程读到该数据 < 人眼可见的画面变化
```

尽量往右走。Agent 最容易停在最左边。

### ③ 这个状态是新读的，还是我记忆里的？

重跑一次读取，别信自己三分钟前的结论——尤其是**中间发生过重启、重载、外部程序介入**的时候。

### ④ 有没有第三方在中间改变了事实？

写文件时杀毒软件在扫、测试时系统服务占着端口、配置生效前页面缓存了旧代码。
**"环境干净"是需要验证的假设，不是默认前提。**

## 怎么处理反例

当你按本库（或任何经验库）操作却得到**相反结果**时：

1. **先信实测。** 经验库是别人的战场地图，地图会过期。
2. **别急着下"这条经验是错的"结论** —— 先确认前提条件是否成立。
   多数"不成立"是 `[本机]` 条目被当成了 `[通病]`。
3. **记录你的环境**：OS + 版本、运行时版本、报错**原文**（不是复述）。
   一句"在我这不行"没法被任何人利用；"PowerShell 7.4 / Windows 11 23H2 / 报错原文 X"是一条新知识。
4. **回馈反例。** 反例本身也是知识——它划定了结论的边界。
