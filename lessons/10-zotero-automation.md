# 10 · Zotero 自动化：锁库只读、Web API 写入、字段索引顺序

> **适用范围**：机制 `[通病]`（"运行中的程序独占 SQLite"、"本地 API 只读"这类设计）；
> 具体接口路径与版本 `[本机]`。
> **谁该读**：要让 Agent 读写 Zotero（或任何"运行中程序 + SQLite + 官方云 API"组合）的人。
> **配套代码**：`recipes/zotero-mcp/`。

---

## 1. 先摸清三条通道，再决定架构

`[本机]` 实测结论（重要：**先探测，别照着文档假设**）：

| 通道 | 能读 | 能写 | 关键限制 |
|---|---|---|---|
| **本地 SQLite**（`zotero.sqlite`） | ✅ | ❌ | **Zotero 运行时文件被独占锁** |
| **本地 API**（`127.0.0.1:23119/api`） | ✅ | ❌ | **默认关闭；且即便打开也只读** |
| **连接器接口**（`127.0.0.1:23119/connector/*`） | — | 部分 | **只能新增条目，改不了已存在的** |
| **官方 Web API**（`api.zotero.org`） | ✅ | ✅ | 需要 key，有速率与版本号语义 |

**结论：读走 SQLite 快照，写走官方 Web API。**
这条组合是在四条路都实测过之后选出来的，不是拍脑袋。

## 2. 运行中的 SQLite：`database is locked`，而且 `busyTimeout` 救不了 `[通病]`

### 症状

```
Error: database is locked
```

即使设了 `busyTimeout`（甚至设得很大）依然如故。

### 根因

**桌面应用常常以独占方式持有它的 SQLite 文件**（或者长期持有写事务）。
SQLite 的 `busyTimeout` 解决的是"**短暂**的锁竞争"，
而这里是**对端根本不打算在你有生之年释放锁** —— 等多久都没用。

### 解法：**复制一份快照再读**

```
1. 把 zotero.sqlite（以及需要的 -wal / -shm，若有）复制到临时目录
2. 打开**副本**（只读）
3. 查询、用完删掉
```

**这个方案的两个额外好处**：

- **Zotero 开着也能用**（不需要求用户关掉软件）
- **Zotero 没开也能用**（不需要求用户打开软件）

> 📌 **通用模式**：*面对"被独占的本地数据文件"，"复制快照读"几乎总是比"等锁 / 求用户关程序"更好。*
> 只要文件不是很大（`[本机]` 的库 13 MB 量级），复制成本可以忽略。
> 注意：**WAL 模式下必须连 `-wal` 一起复制**，否则读到的是旧状态。

### 验证

跑一次读取，**在 Zotero 正开着的情况下**，确认查询返回了数据（不是 0 条、不是报错）。
这个测试必须**开着软件做**，否则证明不了什么。

## 3. 本地 API：默认关闭，**而且只读** `[本机]`

### 症状

想通过本地 API 改数据，结果：

```
PUT    /api/users/0/items/XXXX   → 501 Not Implemented
DELETE /api/users/0/items/XXXX   → 501
PATCH  /api/users/0/items/XXXX   → 501
```

### 根因

Zotero 的本地 API 是**为"只读集成"设计的**（给别人读数据、做插件/脚本查询）。
**写操作根本没实现**，返回 501 而不是 403。
"[501 而不是 403]"这个细节很重要：它说明这是**能力缺失**，不是权限问题 ——
所以你**申请再高的权限也没用**。

### 决策

`[本机]` 评估后**没有**去开启本地 API，理由：

- 开启它需要**关掉 Zotero 改 `prefs.js`**（麻烦、有风险）
- 而它**仍然只读** —— 收益（读）已经被"SQLite 快照"覆盖了
- **收益不值当**

> 📌 **通用决策法**：把每条路的"能做什么 / 开启成本 / 风险"列出来。
> **如果一条路的能力被你已有的路完全覆盖，那它的开启成本就是纯粹的负收益。**

## 4. 连接器接口：能加不能改 `[本机]`

`127.0.0.1:23119/connector/*` 是给浏览器插件用的抓取接口。实测可用：

```
ping                    ✅
getSelectedCollection   ✅
getTranslators          ✅
saveItems               ✅（能新增）
```

**限制：只能新增条目，改不了已存在的条目。** 所以：

- **"抓一篇新文献进来"** → 可以走它
- **"给已有条目加标签 / 改标题"** → 走 Web API

## 5. 写：走官方 Web API 的注意事项

- **key 需要 `write` / `files` / `notes` 权限**（只读 key 写不了）
- **有"版本号"语义**：更新要带当前版本，冲突时返回 **412**。
  正确处理是**重新取一次最新版本再改**，而不是盲目重试（会一直 412）
- **有速率限制**：批量操作要节流
- **附件上传**流程更复杂（要单独传文件），`[本机]` **没实现** ——
  要挂 PDF 得在客户端操作，或者后续补
- **凭据放文件**：`~/.<app>/<key-file>`，ACL 限制为仅当前用户可读（→ [04](04-mcp-stdio-bridge-authoring.md) 规则 4）

---

## 6. 元数据抓取：DOI 走 Crossref、arXiv 走 arXiv 预印本接口

录入新文献时，**不要手打元数据**：

```
有 DOI     → Crossref
有 arXiv ID → arXiv API
```

**两个必备设计**：

1. **`dryRun` 预览**：先返回"我准备写入什么"，让人/Agent 确认，再真的写
   （→ [04](04-mcp-stdio-bridge-authoring.md) 规则 5，破坏性操作要有门禁）
2. **查重**：写入前先按 DOI 查一遍库，避免重复条目

## 7. 一个真实的 bug：**索引构建顺序**导致全文检索永远为空 `[通病]`

### 症状

全文检索工具**永远返回 0 条**，但库里明显有内容。没有任何报错。

### 根因

实现里在**建立索引之前**先"剥离了内部字段"（为了不把内部元数据暴露出去），
结果**被检索的正文也被一起剥掉了** → 索引里是空的。

### 教训

> 📌 **"先清理再索引"和"先索引再清理"是两个不同的东西。**
> 这类 bug 的可怕之处在于**它是静默的** —— 不报错、不崩溃，只是永远返回空。

**这也再次印证 [01](01-verification-discipline.md) 的第 2 问**：
如果当时的验证是"工具调用没有报错"，这个 bug 会一直活着。
真正的验证是**"拿一个确定存在的关键词去查，断言结果非空"**。

## 8. 架构总结（可直接抄）

```
                    ┌─────────────────────────┐
   读 ──► 复制快照 ──►│ zotero.sqlite (只读副本) │  ← Zotero 开/关都能用
                    └─────────────────────────┘
                    ┌─────────────────────────┐
   写 ──► HTTPS  ──►│ api.zotero.org (Web API)│  ← key: write/files/notes
                    └─────────────────────────┘
   "抓新条目" ─────► 127.0.0.1:23119/connector/saveItems   ← 只能新增

   封装成一个零依赖 stdio MCP 服务 → 见 04 与 recipes/zotero-mcp/
```

**验证清单**：

- [ ] Zotero **正在运行时**，读取返回正确条数（不是 0）
- [ ] 搜索一个**确定存在**的关键词，结果**非空**（防第 7 节那种静默 bug）
- [ ] 全文检索命中已知文本
- [ ] `dryRun` 能正确预览将要写入的内容
- [ ] 真实写入一次测试条目 → **回到客户端界面确认它真的出现了**（不要只看 API 返回 200）
- [ ] 凭据文件权限仅当前用户可读

---

## 9. 边界与伦理

- 用户的文献库属于**个人资料**。**不要把库内容、分类结构、研究主题复制到任何公开仓库**。
- 批量修改（打标签、改分类）前**先说明**，最好先 `dryRun` 一遍看影响面。
- Zotero 官方 API 的使用要遵守其服务条款与速率限制。
