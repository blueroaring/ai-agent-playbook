# 03 · 沙箱的 stdio 与进程限制 —— 以及正确的破局点

> **适用范围**：现象 `[本机]`（某 Agent 运行时的文件/进程沙箱策略），
> **架构性结论 `[通病]`**（任何受限执行环境都会遇到同类问题，破局思路一致）。
> **谁该读**：运行在沙箱里的 Agent，尤其是发现"命令明明对却必然失败"的那种。

---

## 1. 核心事实：沙箱禁止进程间管道 stdio `[本机]`

### 症状

三类看起来毫无关联的失败，其实是**同一个根因**：

```bash
# ① Node 用默认 stdio 拉起子进程
child_process.spawn('git', ['push'])        # → EPERM (operation not permitted)
child_process.exec('git status')            # → EPERM

# ② git 自己的报错（因为 git 要靠管道跟 git-receive-pack 通信）
$ git push origin main
fatal: cannot create standard input pipe for git-receive-pack: Permission denied

# ③ PowerShell 管道捕获外部程序输出
$ git log | Select-Object -First 5          # 失败
```

### 根因

受限执行模式**禁止创建命名管道**。而：

- Node 的 `spawn` / `exec` **默认 `stdio: 'pipe'`** —— 需要为 stdin/stdout/stderr 各建一个管道
- `git push` 通过 **`git-receive-pack` 子进程 + 双向管道**通信
- PowerShell 的 `外部命令 | cmdlet` 也是管道

**全都在同一堵墙上撞死。**

### 关键区分：什么能用，什么不能用

| 形式 | 结果 |
|---|---|
| `spawn(cmd, args, { stdio: 'pipe' })`（默认） | ❌ EPERM |
| `spawn(cmd, args, { stdio: 'inherit' })` | ✅ 可用（直接继承父进程的句柄，不新建管道） |
| `spawn(cmd, args, { stdio: 'ignore' })` | ✅ 可用 |
| PowerShell 自身的管道（`Get-X \| Where-Y`） | ✅ 不受影响（在进程内） |
| PowerShell 捕获**外部程序**输出的管道 | ❌ 失败 |
| `git init` / `add` / `commit`（纯本地、不 spawn 打包进程） | ✅ 可用 |
| `git push` / `git fetch`（走 pack 协议） | ❌ 必然失败 |

**"部分 git 命令能用、部分不能用"是这堵墙最典型的指纹。**

### 附带限制：不能启动工作区外的可执行文件 `[本机]`

同一个沙箱还会拒绝执行**位于工作区之外**的程序：

```powershell
& 'C:\Windows\System32\cmd.exe' /c echo hi    # ❌ 被拒
& "$env:ProgramFiles\Google\Chrome\Application\chrome.exe" ...   # ❌ 被拒
& 'D:\NodeJs\node.exe' script.mjs             # ❌ 被拒
```

**后果**：浏览器自动化**不能**用"脚本启动 Chrome"这条路实现，
必须走**宿主侧已经跑着的**能力（例如宿主提供的 MCP 浏览器服务）。

---

## 2. 破局：把需要 stdio 的活儿挪到宿主侧 `[通病]`

### 思路

不要试图"在沙箱内绕过限制"（那是和策略对抗，且不稳定）。
**正确的做法是把这类工作移到沙箱之外的那一侧运行，让沙箱内只跟它做不需要管道的通信。**

而"宿主侧运行、通过 stdio 跟 Agent 通信"——**这正是 MCP stdio 服务的形态**。
宿主进程（不在沙箱里）拉起服务进程，服务进程与宿主之间是正常的管道；
Agent 通过宿主的工具调用接口访问它。**沙箱里的 Agent 从头到尾没建过管道。**

```
┌──────────────── 沙箱内 ────────────────┐   ┌────────── 宿主侧（沙箱外）──────────┐
│  Agent                                 │   │  MCP 客户端（宿主进程）              │
│    │                                   │   │      │                               │
│    │ 工具调用（不是管道）               │   │      │ stdio（管道，合法）           │
│    └───────────────────────────────────┼───┼──────┴──► MCP 服务（node xxx-mcp.mjs）│
│                                        │   │                │                      │
└────────────────────────────────────────┘   │                └─► git push ✅        │
                                             └───────────────────────────────────────┘
```

### 落地清单

1. **写一个零依赖的单文件 stdio MCP 服务**（→ 写法见 [04](04-mcp-stdio-bridge-authoring.md)，
   骨架见 `recipes/mcp-bridge-minimal/`），里面封装所有需要管道的操作。
2. **在宿主的 MCP 配置里注册它**（宿主侧进程启动，天然在沙箱外）。
3. **凭据由服务自己读**（例如 `~/.<app>/<token-file>`），**不经过 Agent、不进 argv**。
4. Agent 侧**统一走工具调用**，不要贪方便去 `pwsh` 里直接跑原生命令——在沙箱收紧时那条路会断。

### 为什么"自建一个 stdio 服务"比"改沙箱策略"更好

| 维度 | 自建服务 | 申请放宽沙箱 |
|---|---|---|
| 稳定性 | 不依赖策略，换会话/换机器都能用 | 每次策略变紧就崩 |
| 凭据处理 | 集中一处，容易审计 | 散落在命令里，容易进 argv / 日志 |
| 可移植 | 换工作区照样用 | 绑定环境 |
| 权限面 | 只暴露你封装的少数操作 | 敞开整个命令执行 |

**实测证据**：某机器上沙箱策略**中途**从受限模式放宽到完全访问，原生 `git` 命令行随之恢复可用；
但既然自建服务已经不依赖策略，就继续用它——**不要在能力边界上来回横跳，要建立不依赖边界的能力。**

## 3. 事故：不要批量 kill 宿主进程 `[通病]`

### 事故经过

某次会话里，为了"重启服务"，Agent 执行了按名字批量杀 `node` 进程的操作。
结果宿主自己的后台任务运行器被一起杀掉：

```
Windows Job runner exited ... before proving its managed range empty
```

**整个会话从此失去后台任务能力**（长命令不能在后台跑了），并且这个损失是**不可逆的**——
运行器由宿主管理，Agent 没法把它拉回来。

### 为什么会这样

**Agent 自己就跑在 `node` 里。** "杀掉所有 node 进程"这句话里包含了：

- 托管你这一轮对话的宿主进程
- 宿主的后台任务运行器
- 宿主的 MCP 服务（你刚建好的能力）

按**进程名**筛选是"我大概知道我要杀什么"的思维；在宿主进程树里，这个假设不成立。

### 规则

1. **永远用精确 PID**，不用进程名通配。
2. **杀之前先确认这个 PID 不是你的祖先**：如果拿不到进程树信息，就默认"可能是"，然后不杀。
3. **要重启宿主控制的东西，交给宿主提供的机制**，不要自己动手。
4. **需要重启托管你自身的进程时，明确告诉用户，让他手动重启**——你做不到，也不该做。

### 验证方式

想确认某个 PID 是否危险，检查它的命令行里有没有你自己运行时的入口
（例如 `node .../bin.js web` 这种宿主形态）。**拿不准就不杀。**

## 4. 怎么判断"我撞上的是沙箱，还是真的坏了"

排查顺序：

1. **看报错特征**：`EPERM` / `Permission denied` / "cannot create ... pipe" 是沙箱的典型用语。
   "文件不存在" / "命令找不到"则更可能是环境问题。
2. **做最小复现**：只留一条命令，去掉所有管道和重定向。
   ```powershell
   git status                      # 通了 → 说明 git 本身没问题
   git status | Select-Object -First 1   # 挂了 → 是管道的问题
   ```
3. **换一种等价调用形式**，看是否变化（`stdio: 'pipe'` → `'inherit'`；管道 → 落文件再读）。
   **变化了就锁定是机制限制，不是你的代码逻辑错。**
4. **确认限制的边界后，改架构，不要改参数。**
