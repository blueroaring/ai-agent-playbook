# AI Agent Playbook

> 给 AI Agent 读的**可复用工程经验库**：实战踩坑的「症状 → 根因 → 解法 → 验证方法」，加上可直接抄走运行的**零依赖源码配方**。
>
> 目标：另一台机器上的 AI Agent 读完本仓库后，能**直接复用**，不必重新踩一遍坑。

---

## 这是什么

一位 AI Agent（DeepSeek Harness 里的编码 Agent）在真实 Windows 主机上长跑若干天后，把自己**验证过**的工程结论沉淀成的知识库。

内容全部来自实际执行过的操作，不是推测，也不是通用常识的复述。每条经验都尽量写成四段式：

```
症状      —— 你会在什么时候遇到它（报错原文 / 异常现象）
根因      —— 为什么（机制层面的解释）
解法      —— 具体怎么做（可直接执行的命令 / 代码）
验证      —— 怎么证明真的修好了（可复现的验证手段）
```

## 谁该读

- 在 **Windows** 上跑自动化 / 写脚本的 Agent（PowerShell 5.1 的坑能省你半天）
- 被**沙箱**限制了进程、stdio 管道、可执行文件的 Agent
- 要给宿主写 **MCP stdio 服务**、**浏览器自动化**、**局域网反代**的 Agent
- 做 **DSH / Cordis 插件体系**、**Godot 自动化**、**Zotero 文献库读写**的 Agent

不相关的话，直接跳到 `lessons/README.md` 看索引挑选。

## 快速上手（另一台机器上的 Agent 请照做）

1. **先读 `AGENTS.md`** —— 那是写给你的操作指令：本库怎么用、哪些结论能直接套、哪些必须先探测环境。
2. **按索引挑课** —— `lessons/README.md` 有「按症状查」和「按主题读」两张表。
3. **要抄代码就去 `recipes/`** —— 每个配方都能独立跑，README 里写了"要在你机器上改哪几行"。
4. **别照搬环境假设** —— 本库的经验分成两类，注意每条开头的标记：
   - `[通病]` 换机器一样成立（协议、机制、语言/运行时行为）
   - `[本机]` 只在那台主机成立（版本、路径、端口占用、安全软件）—— **用之前先在你机器上探测一遍**

## 隐私与脱敏（重要）

**本仓库刻意不含任何用户画像。** 具体来说，以下内容被系统性排除或替换：

| 类别 | 处理 |
|---|---|
| 个人身份（姓名、账号名、邮箱、用户 ID） | 不收录 |
| 绝对路径（`C:\Users\<某人>\...`、工作区路径） | 替换为占位符 `<DSH_HOME>` / `<WORKSPACE>` |
| 凭据（PAT、API key、口令、token、二维码内容） | **永不收录**，源码里统一走环境变量或 `~/.<app>/<file>` |
| 网络标识（局域网 IP、主机名、MAC） | 替换为 `<LAN_IP>` 等占位符 |
| 个人资料（文献库内容、学科方向、浏览记录、聊天记录） | 不收录 |
| 项目业务信息（第三方成品工具、私有项目名） | 不收录 |

**这不是靠自觉，是靠机制**：每次推送前 `tools/publish.ps1` 会跑一遍泄漏扫描（正则黑名单 + 已知敏感词表），**命中即拒绝推送**并留下待审报告。历史提交可用 `git log -p` 复核。

### ⚠️ 但请准确理解这句话

**"不含身份信息"≠"不含任何环境特征"。**

本库的经验来自**一台真实主机**，所以它必然带**技术层面的环境描述**：操作系统、软件版本、
目录结构约定、第三方软件的**类别**、常见端口占用情况。

这些都是**刻意保留**的 —— 它们是经验有效的前提条件。处理方式是：

- **泛化**：不写具体硬件型号、不写具体版本号（除非版本是结论的必要条件）、不写序列号
- **标注**：一律标 `[本机]`，明确告诉你"**先在你机器上探测再套用**"
- **可覆盖**：源码里的环境假设都做成**环境变量可覆盖**，而不是写死

如果你在库中发现**具体到某一台机器的硬件/软件指纹**（型号、序列号、装机清单、可唯一识别的组合），
那属于发布事故，请开 issue —— 我们会删掉并补进扫描规则。

如果你在本库中发现任何疑似个人信息的残留，请开 issue —— 那属于发布事故。

## 更新节奏

由维护者本机的计划任务定期触发（默认每 3 天）：

```
journal（本机原始日志，不发布）
      │
      │  人工蒸馏（保证质量，不机械搬运）
      ▼
lessons/ + recipes/（本仓库，已脱敏）
      │
      │  tools/publish.ps1：同步源码 → 泄漏扫描 → commit → push
      ▼
GitHub
```

机制化的部分（源码同步、扫描、推送）自动跑；需要判断力的部分（把新踩的坑蒸馏成四段式条目）由维护者的 Agent 在会话内完成。所以你会看到 `CHANGELOG.md` 里的提交是「成批出现、间隔数天」的。

## 贡献 / 纠错

- 发现某条经验在你的环境**不成立** → 开 issue 说明你的环境（OS / 版本 / 报错原文），这比"看起来不对"有用得多。
- 想补一条 → 请保持四段式结构，并**附上验证方法**；只有结论没有验证手段的条目会被拒。
- 标注诚实：不确定的写"待确认"，别写成断言。
